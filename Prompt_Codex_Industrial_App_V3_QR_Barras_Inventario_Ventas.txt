TIPOS Y CATEGORÍAS
El selector de registro debe ofrecer exactamente tres categorías principales:
1) Producto terminado: bolsas por presentación (250 g, 500 g y presentación configurable), cada bolsa física tiene un ID/código propio; agrupable por lote. La presentación/SKU agrupa, pero NO identifica individualmente una bolsa.
2) Materia prima: avena, soya, cacahuate, canela, y otras que se agreguen; una etiqueta identifica un LOTE/CONTENEDOR de materia prima, con cantidad y unidad (kg, g), fecha de recepción y ubicación, no cada gramo; permitir entradas/consumos y agotamiento con movimientos auditables.
3) Maquinaria: cada activo físico tiene identificación individual, código de equipo, descripción, modelo/serie opcionales, ubicación, mantenimiento y estado. Distinguir equipos de la propuesta aún no adquiridos de activos realmente dados de alta. No asignar códigos de activo físico a un equipo que solo aparece como propuesta sin confirmación.
Si los catálogos del proyecto incluyen empaques y equipos auxiliares, permitir extensiones consistentes sin alterar las tres categorías principales.

IDENTIFICADORES Y SIMBOLOGÍAS
- Implementa QR y barras lineales Code 128 para cada identificador, usando EXACTAMENTE el mismo ID estable y normalizable. El QR debe codificar una cadena interna legible por el lector y funcional sin internet, NO un enlace de localhost ni datos privados. Por ejemplo: ID interno opaco 'PT-<aleatorio>', 'MP-<aleatorio>', 'MQ-<aleatorio>'. El lector QR y el de barras deben poder resolverlo al mismo registro mediante normalización estricta.
- Utiliza IDs opacos generados con fuente criptográficamente aleatoria y con al menos 80 bits efectivos (p.ej., 20 caracteres hexadecimales de uuid4) + prefijo de categoría. Validar unicidad con índice UNIQUE de SQLite y reintentar en una colisión; nunca generar a partir del contador de filas solamente.
- No afirmar que los códigos sean GTIN/EAN-13/GS1 oficiales: Code 128 es para trazabilidad INTERNA. No crear códigos comerciales que aparenten estar asignados por GS1.
- Evita barras que dependan de caracteres no soportados, y permite imprimir el ID al pie de forma legible. No guardar una imagen como único registro: guardar siempre el identificador y metadatos de negocio.

TRANSACCIONES CRÍTICAS
1) Alta de código y de inventario: una sola transacción genera el ID único y registra el artículo. Generación masiva de producto por lote con N etiquetas = N bolsas físicas y N IDs diferentes. El número N debe ser entero positivo y estar limitado a un rango razonable con confirmación para lotes grandes. Si falla el PDF después de la transacción, permitir reimprimir los códigos existentes sin generar un lote nuevo.
2) Reimpresión: buscar por código, lote, filtros/categoría y descargar etiquetas existentes; nunca insertar filas nuevas.
3) Venta: entrada por lector USB tipo teclado o escritura/pegado manual; resolver el QR y Code128 al mismo ID. Al consultar mostrar nombre, presentación, precio, lote, estado y disponibilidad. Solo se venden unidades de producto terminado con estado DISPONIBLE y precio definido. Validar carrito sin duplicados y confirmar una única transacción DB: venta + líneas + cambio de estado a VENDIDO + movimientos de salida + auditoría. Usar condición transaccional (UPDATE ... WHERE status='DISPONIBLE', rowcount=1 y restricción UNIQUE sale_lines(traceable_item_id)) para evitar doble venta en dos sesiones. Venta repetida o código inexistente debe mostrar error claro y NO descontar inventario de nuevo. En caso de fallo de cualquier línea, rollback íntegro de la venta. Prevenir doble clic/reintentos mediante operation_id persistido; devolver resultado de la misma operación en vez de duplicarlo.
4) Inventario activo: filtrar solo DISPONIBLE / materia prima con saldo positivo / maquinaria activa, con pestañas por categoría. Los productos VENDIDOS desaparecen de existencia disponible, pero permanecen visibles en historial/consulta con estado VENDIDO, fecha, referencia de venta.
5) Anulación de venta: opcional si es segura y probada; exigir razón, generar evento de reverso e impedir reversos duplicados; nunca borrar historial. Si no se implementa, documentar explícitamente que se requiere corrección manual administrativa y no ofrecer botón engañoso.
6) Materia prima: permitir consumir una cantidad válida <= saldo en la misma transacción, con kardex, bloqueando saldos negativos. Maquinaria: solo cambios de estado auditados (ACTIVO, EN_MANTENIMIENTO, FUERA_DE_SERVICIO); no incluirla como venta de producto por defecto.
